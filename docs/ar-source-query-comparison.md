# 从上游单据查询应收：单头与明细分表、合表对比

评估基于 2026-11-07 的仓库实现和 MySQL 8.0.42 正式迁移，面向销售出库单、税费单和运费单的详情及列表页面。

**建议保留应收单头和价税明细，优先提供统一的来源反查接口。** 外部单据查询的首要条件是能够通过稳定的上游身份找到应收行。现有来源表已经按来源系统、单据类型和单据 ID 建立索引。对于最常见的“本单产生了哪些应收、还欠多少”，查询只需来源表和明细表。返回应收单号、单头状态或到期日时才需要单头。

## 先定义用户点开的关联范围

假设出库单 OUT-1 产生应收 AR-1，后续运费单 F-1 产生 AR-2，税费单 T-1 产生 AR-3。三次生成各自保留真实来源。

| 用户入口与期望 | 正确的关联方式 | 必须约定的边界 |
| --- | --- | --- |
| 运费单 F-1 打开“本单应收” | 以系统、运费单类型、F-1 的内部 ID 精确查直接来源 | 一个来源可能产生多张应收，也可能同时产生价款和税额两行 |
| OUT-1 打开“本单应收” | 同样按 OUT-1 的直接来源查 AR-1 及其他直接以 OUT-1 生成的应收 | F-1、T-1 自己生成的应收拥有各自的来源身份 |
| OUT-1 打开“相关费用及应收” | 若业务定义为同组，先找到起始业务组，再按组查应收行。若业务定义为源自该出库单，则由上游提供关联的费用单身份，或保存明确的出库单与费用单关系 | 同组只证明共同结算。一个组含多张出库单时，同组扩展会多查；独立税费组会漏查。需在页面区分直接来源、关联费用和各自归属 |
| 出库单列表显示每单应收余额 | 按本页来源身份集合批量匹配，按来源、币种、金额类型聚合 | 同一应收单含多个来源时，只累计该来源命中的行；同组统计不能重复累计到每个来源上 |

以主体限定授权范围，使用来源内部 ID 做关联，单据编号用于展示。行级查询应区分“单据全部来源行”“指定行 ID”和“仅无行号的来源槽”。现有上游作废查询中 NULL 表示精确匹配无行号槽，将其直接用于整单浏览会漏掉有行号的记录。

## 收益与成本矩阵

A 为现有单头、明细、来源三类记录。B 仅合并单头和明细，每行仍表示价款或税额，并保留来源表。将来源字段也内联是另一个设计选择，见表后说明。

| 比较维度 | A 分表 | B 合表 | 对上游页面的影响 |
| --- | --- | --- | --- |
| 接入便利性 | 可由后端封装来源反查，页面一次请求 | 同样可封装为一次请求 | 两者均可做到一次调用。现有应收分页只接受主体及可选客户，页面目前缺少来源筛选 |
| 查询命中行、应收 ID 和未核销余额 | 来源索引定位后按行主键读取明细，直接得到 document_id 和 open_amount | 来源索引定位后按主键读取合并行 | 两者都是两表路径，合表在此处没有减少关联；合并行更宽，实际页读取量要测 |
| 同时展示应收单号、到期日、单头状态 | 从命中明细取得 document_id，批量或一次 SQL 关联单头主键 | 命中行已经包含单头字段 | B 可省一次逻辑关联。A 可以对文档 ID 先去重再取头，多条明细指向同一单头时尤其值得比较 |
| 一张上游单据多次生成；按应收单分页 | 命中明细后按 document_id 去重、计数与分页，再取单头 | 同样要按共享单据标识去重、计数与分页 | 两者都不能先分页明细再去重，否则会出现短页、跨页重复和错误总数 |
| 上游列表批量展示余额 | 批量聚合匹配行，通常无需单头 | 同样可批量聚合，但扫描的业务行更宽 | 避免列表逐单发请求通常比减少一次单头关联更值得优先验证 |
| 由出库单追溯独立费用单 | 通过准确的上游关系或约定的业务组扩展 | 需要相同的关系数据 | 合表本身不会产生 OUT-1 与 F-1、T-1 的关联 |
| 创建、存储与索引 | 每次生成写一个单头和 N 行，单号、状态及到期日各存一份 | 少写一个单头，但 N 行重复保存单头字段，按这些字段建索引也会增加索引项 | 独立单行补费对 B 最有利。中等比例的多次生成，不能直接推出单行单占比 |
| 余额更新、整单作废与审计 | 按行更新余额，单头提供整单版本与锁定对象 | 可按行更新余额，另需保证多行单的公共字段、整单状态和版本一致 | B 的写入成本应计入并发核销与作废，不能只比较创建 INSERT 数 |
| 迁移与兼容 | 可增量增加只读接口并独立上线 | 须保留逻辑单据 ID，迁移依赖并兼容原有审计、查询和作废语义 | B 的准入条件应是端到端性能收益足以承担迁移和长期维护成本 |

**如果真正想省掉来源表关联**，还可单独评估在明细上内联直接来源，与是否合并单头无关。它能让直接来源查余额有机会成为单表查询，代价是明细行及索引变宽、无来源行携带空字段，并需迁移来源事件输出唯一约束与原有追溯记录。若同一明细还要按出库单、运费单等多个角色反查，一个来源字段组合仍只能表示一个直接来源。

## 推荐的查询方式

建议新增只读接口，按授权主体及来源身份返回匹配明细或应收单摘要。列表调用提供批量来源参数。单头摘要应分别命名“本来源匹配金额”和“整单金额”，作废行可查历史，但其原额应与当前有效应收分开汇总。下列 SQL 表示直接来源查有效余额的最短路径，参数由后端绑定：

```sql
SELECT l.document_id, l.currency, l.amount_type, SUM(l.open_amount) AS source_open_amount
FROM oms_ar_line_source AS s
JOIN oms_ar_line AS l ON l.id = s.line_id
WHERE l.legal_entity_id = :legalEntityId
  AND s.source_system = :sourceSystem AND s.source_type = :sourceType
  AND s.source_id = :sourceId
  AND s.delete_status = FALSE AND l.delete_status = FALSE AND l.status = 'ACTIVE'
GROUP BY l.document_id, l.currency, l.amount_type;
```

现有索引 ix_source_document(source_system,source_type,source_id) 可用于筛选，line_id 另有唯一索引。来源表没有 legal_entity_id，授权过滤必须通过明细或其他可信范围关系完成。实际执行计划由数据分布决定。只有回表读取 line_id 成为实测瓶颈时，才对照测试把 line_id 放在来源检索索引末尾的收益与新增写入成本。若瓶颈是来源覆盖范围或按单去重，则应分别补业务关系或评估按来源到应收单的查询映射。

## 性能验证与决策门槛

本次本机 Docker 服务未连通，以上是基于 SQL、索引和访问粒度的结构分析。尚无 A/B 延迟或吞吐实测数据。

1. **按真实分布造数。** 分别采集每个来源产生的应收单数、每单价税行数、每页来源数和热点来源并发量。包括普通出库、多次补费、单行补税、多来源同单、独立税费组和已作废历史。
2. **在同一 MySQL 8.0.42 环境比较。** A、B 使用相同数据、业务返回字段、事务语义和可比索引。分别测直接来源查余额、分页含单头、整页批量查询，以及并发创建、核销和作废。记录冷热缓存下的 P95/P99、吞吐、实际扫描行数、临时表和排序、锁等待、表与索引大小及写入日志量。用 EXPLAIN ANALYZE 确认耗时发生在哪一步。
3. **先验正确性，再判断性能。** 相同来源的两方案结果应逐行相等，分页无重复，金额不串来源、主体或币种。若分表加统一查询已达到页面响应目标，保留分表。仅在含单头查询占主要负载、单头关联确为主要瓶颈，且 B 在等价写入负载下仍满足业务目标时，启动合表迁移评审。具体延迟目标应由页面使用方与服务方在压测前确定。
